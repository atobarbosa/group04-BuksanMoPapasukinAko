# BuksanMoPapasukinAko: Network Intrusion Anomaly Detector

A machine learning project that detects network anomalies. This containerized web application takes network traffic logs and predicts whether the traffic is normal background activity or a cyberattack.

Manually reading network logs takes too much time for IT administrators. This project tries to solve that by using a Random Forest model to classify traffic automatically. We built a simple frontend where a user uploads a `.parquet` file and gets the results on their screen. The entire application runs inside Docker containers so it won't have dependency issues on different machines.

## System Architecture

The project uses a containerized 3-Tier Architecture:

1. **Presentation Layer** — A Gradio web interface container that allows users to upload network logs and view anomaly reports, including a scan history panel.
2. **Logic Layer** — A FastAPI server container that preprocesses incoming data, handles unseen network protocols safely, runs the data through the trained Random Forest model, and logs each scan to a history file.
3. **Data Access Layer** — In-memory processing of uploaded tabular files; scan history persisted as flat CSV inside the API container.

The UI and API run as separate services on a shared Docker network defined in `docker-compose.yml`. The UI reaches the API by its service name (`api`), not `localhost` — containers don't share a loopback interface with each other or the host by default.

Preprocessing logic (label encoding with safe fallbacks, and leakage-safe feature/target splitting) is shared across training, evaluation, and inference through `preprocessing.py`, so all three stages apply the exact same rules.

## Dataset

We trained our model using the [UNSW-NB15 dataset](https://research.unsw.edu.au/projects/unsw-nb15-dataset), which contains metadata for normal network traffic and several types of simulated attacks. We use the `.parquet` version of the dataset for faster read times.

## Model Performance

Evaluated on the held-out UNSW-NB15 test set:

| Metric | Score |
|---|---|
| Accuracy | 86.81% |
| Precision | 82.16% |
| Recall | 97.14% |

**What this means in practice:** the model is tuned to prioritize catching real attacks over avoiding false alarms. It misses only about 3% of actual attacks (high recall), which is the right tradeoff for a security tool — a missed attack is far more costly than a false alarm.

The cost of this tradeoff is precision: roughly **1 in 5 events the model flags as an attack is actually normal traffic**. In practice, this means:

- Treat "anomaly detected" as a signal to investigate, not automatic proof of an intrusion.
- On busy networks, expect a meaningful number of false positives in every scan — this is expected behavior, not a bug.
- This tool is a triage aid for IT administrators, not a fully automated, zero-review intrusion response system.

## Features

- **Anomaly scanning** — Upload a `.parquet` network log and get a binary normal/attack classification per event, plus aggregate totals.
- **Attack category breakdown** — If the uploaded file includes ground-truth `attack_cat` labels (true for labeled datasets like the UNSW-NB15 test set; not present in real unlabeled traffic), the API surfaces a breakdown of which attack types were flagged. This is purely informational — `attack_cat` is never used as a model feature.
- **Scan history** — Every scan is appended to `scan_history.csv` inside the API container (timestamp, filename, totals, safe/flagged status). The UI displays the 10 most recent scans.
- **Fully containerized** — No local Python installation required to run the app. Both services build and start with a single `docker compose up` command.

## Known Limitations

- Trained and evaluated on the UNSW-NB15 dataset only; performance on live, real-world traffic from other networks or protocols not represented in this dataset is unverified.
- Unseen/novel categorical values (e.g. a protocol not present during training) are mapped to a default known category rather than flagged separately — this prevents crashes but means genuinely new traffic types won't be specially highlighted.
- No temporal/sequential modeling — each event is classified independently, so multi-step or slow-burn attack patterns spanning many events aren't explicitly modeled.
- Upload size is capped at 50 MB per scan.
- The attack category breakdown only appears for labeled test/demo data; it will not appear when scanning real unlabeled production traffic.
- **`scan_history.csv` is not persisted outside the API container.** Running `docker compose down` (or rebuilding the API image) resets scan history, since no volume is currently mounted for it. Adding a volume mount is a natural next improvement.
- **`.pkl` model files are baked into the API image at build time.** Retraining the model (`train.py`, run locally) requires rebuilding the API image (`docker compose up --build api`) for the new model to take effect — there's no hot-reload of the model file.
- `requirements.txt` uses minimum-version constraints (`>=`) rather than exact pins. This keeps local `uv` installs from failing when an exact old version has no prebuilt wheel, but it also means two separate `docker compose build` runs done far apart in time could theoretically pull in different dependency versions. A locked, exact-pinned requirements file has not been generated yet.
- No automated tests exist for `preprocessing.py` or the API endpoints.
- No CI/CD pipeline — images are built and run manually.

## How to Run the Project (Docker)

You must have **Docker** and **Docker Compose** installed. You do not need to install Python locally to run the app.

```bash
# 1. Clone the repository
git clone https://github.com/atobarbosa/group04-BuksanMoPapasukinAko.git
cd group04-BuksanMoPapasukinAko

# 2. Build and start both containers
docker compose up --build

# 3. Open the app
# UI:  http://localhost:7860
# API docs (Swagger): http://localhost:8000/docs
```

To stop the app:

```bash
docker compose down
```

> Note: stopping and restarting with `docker compose down` / `up` will reset `scan_history.csv`, since it isn't currently mounted to a persistent volume (see Known Limitations above).

## Retraining the Model

The model is trained locally, not inside a container:

```bash
uv pip install -r requirements.txt
python train.py
```

This regenerates `random_forest_model.pkl` and `encoders.pkl` in the project root. Then rebuild the API image so the new model gets copied in:

```bash
docker compose up --build api
```

## Local Development Without Docker

Still fully supported for active development:

```bash
uv pip install -r requirements.txt

python train.py       # one-time, only if .pkl files don't exist
python evaluate.py    # optional sanity check

# Terminal 1:
python api.py

# Terminal 2:
python ui.py
```

Open `http://127.0.0.1:7860`. The API must be running before scanning a file, or the UI will show a connection error (expected behavior).
